# ADR 0010: Verdict comparability requires rubric version, concrete model, and judge context

## Status

Accepted

## Context

`fact_verdict`'s primary key is `(session_id, rubric_version, judge_model)`. That triple is the tool's integrity guarantee: it is what lets `report` claim that a score moved between two windows because the *agent* changed, not because the measurement changed. Two verdicts are only safe to compare, or to conflate on the same key, when three separate things hold: the same rubric version, the same concrete judge model, and the same judge system context. Only the first is obvious from the schema; the other two need to be written down once, because nothing else states them.

**Rubric version** is already enforced correctly: `rubric_version` is a column, and a manual bump invalidates the cache and forces re-scoring. That part of the design was never the gap.

**Concrete model** was the gap this ADR exists to close. `judge_model` held whatever string reached `--judge-model`, defaulting to the alias `"sonnet"`. The scoring loop then overwrote whatever the backend actually used with that same configured alias, so even a backend that knew the real model could not report it. Aliases float: `sonnet` resolves to whichever Sonnet release is current, so two runs a month apart share a cache key while being graded by materially different models. The store reports a delta between the two windows; the delta is measurement drift, not a change in agent behavior. There is no error, no warning, and no way to tell after the fact which model produced a given row. That silent failure mode, not a stylistic preference for precision, is why an alias in the `judge_model` column is not a small imprecision: it is the exact ambiguity the primary key exists to prevent.

The fix reads the concrete identifier from the response envelope's `modelUsage` map, keyed by model ID, rather than from that entry's `canonicalModel` field. Probing the installed CLI shows the two diverge for at least one alias: a `--model haiku` call yields a `modelUsage` key of `claude-haiku-4-5-20251001` (the dated snapshot) against a `canonicalModel` of `claude-haiku-4-5` (the undated family name). Keying identity on the family name would reintroduce this same class of drift one level down: when a new snapshot ships within a family, `canonicalModel` holds still while the underlying model changes, and two different models would again collide on one key. The map key is the more precise identifier the envelope offers, so it is the one read into `judge_model`. Extraction is strict rather than defensive: a `modelUsage` map that is missing, empty, or carries more than one entry raises `JudgeError` instead of falling back to the configured alias. A silent fallback would restore exactly the ambiguity being removed, and multiple entries would mean the call used more than one model, which no single `judge_model` value can represent.

**Judge system context** is the third leg, and it is the one this ADR is chiefly responsible for stating, because it is not a key column and a reader of the schema would not otherwise know it needs to hold. The judge's system context (which hooks, plugins, `CLAUDE.md`, and settings shape its behavior before it ever sees the transcript view) is not recorded per verdict at all. It is held constant structurally: the judge runs in minimal mode (`--bare`), with `--setting-sources user` excluding repo-local `project`/`local` settings that a directory the analyzed agent touched could otherwise use to reconfigure the judge, and with the user's settings file passed explicitly via `--settings` (needed because `--bare` reads `apiKeyHelper` only through `--settings`, not through `--setting-sources`). As long as those flags don't change, every verdict is graded by a judge with the same system context, so the context does not need its own column to make verdicts comparable.

That structural guarantee has a real limit worth stating honestly rather than glossing over. `--settings` loads the *entire* user settings file, not a minimal set of fields constructed in code. The judge context is therefore pinned to that file's contents, not to a minimal context agentlens controls directly. A change to that file (a different `apiKeyHelper`, an added `env` entry, anything else the file can carry) is a judge-context change that the primary key does not capture and that no code path in agentlens detects. The tighter alternative was considered and deliberately deferred: building a minimal `--settings` JSON in code that forwards only `apiKeyHelper` and the base URL would narrow the pinned context to exactly what agentlens intends, at the cost of ceremony that wasn't judged necessary while the settings file is a per-user constant that rarely changes. This ADR is that limitation's record; a future change that narrows the context, or that makes any part of it configurable per run, must reckon with promoting it to a key column rather than assuming the structural guarantee still holds.

## Decision

Two verdicts are treated as comparable, and are allowed to collide on the same `fact_verdict` row, only when all three hold: same `rubric_version`, same concrete `judge_model`, same judge system context.

- `rubric_version` and `judge_model` are enforced through the `fact_verdict` primary key `(session_id, rubric_version, judge_model)`. `judge_model` holds the concrete model identifier resolved by the judge backend from the response envelope's `modelUsage` map key, never the alias supplied at the CLI or via `--judge-model`. The scoring loop does not overwrite the backend's resolved value.
- The judge system context is held constant structurally rather than recorded as a column: `--bare` plus the pinned setting sources and explicit `--settings` path fix the context across every call, so no two verdicts can differ on this leg as long as those flags are unchanged.
- Any future change that makes the judge context configurable per run (a flag to opt into non-bare mode, a per-call settings override, anything that lets the context vary between two calls that would otherwise share a `judge_model` and `rubric_version`) must promote that context to part of the verdict identity (a key column), not merely a documented assumption.

## Consequences

- When a floating alias advances to a new underlying model, every session previously scored under the prior model is correctly reported as unscored under the new one, and a full window re-scores. This is intended, not a defect: it is the same behavior a `rubric_version` bump already produces, for the same reason. The existing confirmation gate and `--max-sessions` are the cost controls for it, not a new mechanism.
- This lands while `fact_verdict` holds zero rows, so nothing needed migrating or re-scoring to take effect. The same change made after a few hundred sessions were scored would mean invalidating real, paid-for work rather than a clean cutover.
- `modelUsage` is an undocumented envelope field that could change shape in a future CLI release. Extraction raises `JudgeError` rather than falling back silently, so a shape change surfaces as a loud failure on the next call rather than quietly reverting to alias-keyed rows that look fine and aren't.
- The judge-context leg is a structural guarantee, not a stored fact, and it is only as strong as the flags in `_build_args()` staying what this ADR describes. A code review touching those flags is a review of verdict comparability, even when nothing about `judge_model` or `rubric_version` changes.
- The judge-context guarantee is weaker than "minimal context constructed in code": it is pinned to the user's settings file as a whole, and an edit to that file outside agentlens is an untracked context change. This is a known limitation, not an oversight, and the narrower alternative (a minimal in-code `--settings` payload) remains available if it ever needs tightening.
